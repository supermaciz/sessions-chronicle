# Heatmap Width Limit - Design

**Date:** 2026-03-09  
**Status:** Implemented [#74](https://github.com/supermaciz/sessions-chronicle/pull/74)  
**Parent:** `2026-03-07-basic-analytics-design.md`

## Problem

The activity heatmap currently renders the full activity history from the first active day to the last active day.
As the indexed history grows, the widget width grows with it and can degrade the analytics layout.

## Decision

Limit the heatmap to a rolling 6-month window ending on the last recorded activity day.

The visible range should be communicated explicitly in the Activity section so users understand that the heatmap is a bounded recent-history view, not a complete lifetime view.

## Why This Approach

- It solves the product problem directly: the heatmap stops expanding indefinitely.
- It keeps the existing heatmap rendering model intact; only the input range changes.
- It matches the user's requested behavior more closely than a raw week-count cap.
- It avoids UI complexity such as horizontal scrolling or clipped custom drawing.

## Scope

This change affects only the heatmap dataset and the Activity section presentation.

It does not change:
- overview counters
- activity day aggregation
- sessions-by-tool, token, or session-span analytics
- database contents or indexing behavior

## Data Semantics

### Window End

The window ends on the last activity day present in `activity_days`, not on the current date.

This avoids showing trailing empty weeks when the user has not used an AI tool recently.

### Window Start

The window start is calculated as 6 calendar months before the last activity day.

If the full activity history is shorter than 6 months, the effective visible history starts at the first real activity day instead.

### Week Alignment

After the visible start and end bounds are determined, the rendered heatmap range is aligned to full calendar weeks:
- start aligned backward to Monday
- end aligned forward to Sunday

This preserves the current 7-row grid layout and month/day label behavior.

### Displayed Range Metadata

`HeatmapData` should carry the effective visible bounds used by the UI.

Recommended additional fields:
- `display_start_day: Option<String>`
- `display_end_day: Option<String>`

These fields represent the real bounded display period before week-padding semantics are re-derived in the UI. They let the UI show a concise range label without inferring it indirectly from rendered cells.

## Architecture

### Database / Analytics Layer

The windowing logic should live in `src/database/analytics.rs` inside `build_heatmap()`.

Instead of always building from the first activity day to the last activity day, `build_heatmap()` should:
1. parse the first and last activity days
2. compute `window_end` from the last activity day
3. compute `window_start` as `window_end - 6 calendar months`
4. clamp that start to the first real activity day when history is shorter
5. align the clamped range to full weeks
6. build zero-filled days only for the bounded aligned range
7. store the effective visible bounds in `HeatmapData`

This keeps the range logic in the same layer that already owns heatmap normalization.

### Model Layer

`src/models/analytics.rs` should extend `HeatmapData` with explicit range metadata.

That avoids duplicating date-range logic in the UI and keeps the heatmap view as a rendering consumer of already-prepared analytics data.

### UI Layer

`src/ui/analytics_heatmap.rs` should continue to render the cells from `HeatmapData.weeks` as it does today.
Its measured width will naturally shrink because `week_count` is bounded.

`src/ui/analytics_view.rs` should render a small textual range label near the Activity section, for example:
- `Oct 2025 - Mar 2026`

The accessible summary/tooltip generated by the heatmap should also reflect the bounded range so it does not imply that the full history is visible.

## UI Behavior

- If the history spans more than 6 months, show only the bounded recent window.
- If the history spans less than 6 months, show the full available history.
- If there is no activity data, keep the existing empty behavior.
- The range label is informational only; it does not become a filter control in this change.

## Alternatives Considered

### 1. Fixed Week Cap

Cap the heatmap to a fixed number of weeks, such as 26.

Rejected because it is less faithful to the requested "6 months" behavior and creates edge cases where adjacent months are represented unevenly.

### 2. UI-Level Width Cap With Scrolling or Clipping

Keep the full dataset and constrain the widget visually.

Rejected because it treats the symptom rather than the product issue, harms readability, and adds interaction complexity to the only custom chart in the page.

## Testing

### Unit Tests

Add or update tests in `tests/analytics_queries.rs` to verify:
- the heatmap is limited to the last 6 months of activity
- the bounded range still aligns to Monday/Sunday full weeks
- short histories remain fully visible
- explicit display bounds in `HeatmapData` match the intended visible range

### UI Tests

Add targeted tests in `src/ui/analytics_heatmap.rs` for summary/range formatting if the tooltip text changes to include or rely on the new display bounds.

### Integration Tests

Update `tests/analytics_integration.rs` so it no longer assumes that the heatmap sum always equals `overview.total_sessions` for arbitrarily old fixture histories.

The integration assertion should instead validate properties compatible with a bounded window, such as:
- the heatmap is non-empty when activity exists
- the max day count remains positive
- the displayed range metadata is populated

## Notes

This is intentionally a bounded, recent-history visualization.
If a future version needs lifetime history exploration, that should be a separate design with filtering or alternate navigation, not an unbounded growth of this widget.
