# Token Cache in Analytics and Token Semantics UX - Design

**Date:** 2026-03-14  
**Status:** Proposed  
**Related:** `2026-03-07-basic-analytics-design.md`, `2026-02-28-token-usage-display-design.md`

## Decision Summary

This design extends token analytics and token explanations without changing the
core `TokenUsage` normalization model.

| Decision | Choice |
|----------|--------|
| Product goal | Show cache activity in Analytics and explain token fields more clearly in the UI |
| UX level | Compact but pedagogical |
| Canonical token model | Keep `TokenUsage` as the shared vocabulary |
| Analytics totals | Keep `total = input + output` |
| Cache handling | Show separately from totals |
| Coverage rule | A session counts as token-reported only when `input_tokens` and `output_tokens` are both present |
| Explanation strategy | Shared concise labels/tooltips across `SessionDetail` and `Analytics` |

## Goal

Users can already see per-session token usage in `SessionDetail`, and they can
already compare input/output totals by AI assistant in `Analytics`.

The current UX still leaves two gaps:

- Analytics hides cache activity entirely
- token labels are factual but not always self-explanatory, especially when
  cache semantics vary across providers

This design adds cache visibility to Analytics and improves token explanations in
both `SessionDetail` and `Analytics`, while preserving the project's existing
semantic caution around cross-provider token accounting.

## Non-Goals

- redefining `TokenUsage` semantics per provider
- changing parser extraction rules for session-level token usage
- introducing cost analytics or currency display
- adding charts or drill-down views specific to cache metrics
- treating cache counters as universally additive to token totals

## Product Principles

### Compact but clear

The UI should explain enough to avoid confusion, but not turn session metadata
or analytics rows into documentation blocks.

### Shared vocabulary

`SessionDetail` and `Analytics` should use the same terms for the same concepts:
`input`, `output`, `total`, `cache`, `read`, `write`, and `reasoning`.

### No false precision

Cross-provider token semantics differ. The UI must explain cache clearly without
implying that cache tokens can always be added on top of input tokens.

## Data Model

### Keep `TokenUsage` as the canonical model

No new session-level token model is introduced.

`src/models/token_usage.rs` remains the shared representation for normalized
session token usage across supported AI assistants.

### Extend Analytics aggregates

`src/models/analytics.rs` should expand `AiAssistantTokenUsage` from:

- `input_tokens`
- `output_tokens`

to:

- `input_tokens`
- `output_tokens`
- `cache_read_tokens`
- `cache_write_tokens`
- `reasoning_tokens`

All five aggregate fields should remain optional so the analytics layer can keep
distinguishing:

- sessions with enough data to count as token-reported
- sessions with partial extra counters such as cache or reasoning
- assistants that do not expose those counters at all

## Analytics Query Semantics

### Reported-session rule stays unchanged

The existing rule in `src/database/analytics.rs` is correct and should remain:

- a session counts toward `reported_sessions` only when both `input_tokens` and
  `output_tokens` are present

This avoids silently treating partial token rows as complete token coverage.

### Aggregation behavior

The analytics query should additionally sum:

- `cache_read_tokens`
- `cache_write_tokens`
- `reasoning_tokens`

These sums should only be taken from sessions already counted as token-reported,
so the section stays internally consistent.

If a reported session has `NULL` for one of those optional fields, that field
contributes nothing to the sum.

### Total semantics in Analytics

For the main per-assistant summary, `total` should remain:

`input + output`

Cache values should not be added to the total because they may overlap with
input accounting depending on the assistant/provider.

Reasoning remains a separately exposed metric in the product model and UI, not
part of the main Analytics total for this iteration.

## SessionDetail UX

The current two-line structure in `src/ui/session_detail.rs` remains:

- `Tokens:` line for input/output/reasoning
- `Cache:` line for read/write

This keeps the metadata card compact and already matches the intended visual
hierarchy.

### SessionDetail copy update

The visible labels stay short:

- `Tokens:`
- `Cache:`

The explanatory tooltips should become slightly more explicit and consistent
with Analytics:

- `Input: tokens sent to the model`
- `Output: tokens generated by the model`
- `Reasoning: extra reasoning tokens when the assistant reports them`
- `Cache read/write: cache activity reported by the assistant; depending on the provider, cache counts may overlap with input tokens`

The goal is to clarify meaning without adding visible prose to the detail card.

## Analytics UX

### Section structure

The existing `Token consumption` section in `src/ui/analytics_view.rs` remains
the single token-focused section.

No new page, drill-down, or chart is introduced.

### Per-assistant row layout

Each assistant row should present token information in two levels.

Primary visible summary:

- `X input / Y output / Z total`

Secondary visible summary when data exists:

- `cache: A read`
- `cache: A read · B write`
- `reasoning: R`
- or both cache and reasoning as a short secondary line

If neither cache nor reasoning is available for that assistant aggregate, the
secondary line is omitted.

### Section-level explanation

The token section should gain a concise explanatory aid near the title or in a
tooltip attached to a short helper label.

That help should explain:

- `input` = tokens sent to the model
- `output` = tokens generated by the model
- `cache` = cache activity, which may already overlap with input depending on
  the assistant/provider

This keeps the section self-explanatory without making every row verbose.

### Missing-data behavior

The existing missing-data copy from the analytics design stays unchanged:

- section subtitle for partial coverage
- `—` per assistant when token data is unavailable
- single descriptive empty row when no assistants report tokens

Adding cache visibility must not degrade this behavior into implied zeros.

## Shared Formatting Helpers

`src/ui/format.rs` should become the single home for token-display wording used
by both `SessionDetail` and `Analytics`.

That includes:

- formatted token fragments (`input`, `output`, `cache`, `reasoning`)
- token tooltip copy
- any short explanatory helper text reused across views

The purpose is consistency, not abstraction for its own sake.

## Edge Cases

### Assistants with no cache fields

If an assistant never reports cache counters, Analytics should show the main
input/output/total line only.

### Partial cache fields

If only `cache_read_tokens` is present, show only `read`.
If only `cache_write_tokens` is present, show only `write`.

### Reasoning without cache

If an aggregate has reasoning data but no cache data, show the reasoning summary
without inventing a cache line.

### Provider-dependent overlap

Where semantics are provider-dependent, the UI should explain overlap risk in
tooltip/help copy rather than trying to normalize it away in totals.

## Implementation Areas

- `src/models/analytics.rs`
- `src/database/analytics.rs`
- `src/ui/analytics_view.rs`
- `src/ui/session_detail.rs`
- `src/ui/format.rs`

## Verification Plan

### Data/query tests

Add or update analytics tests to verify:

- per-assistant sums for input/output/cache/reasoning
- `reported_sessions` still depends only on input+output presence
- optional cache/reasoning fields do not create false token coverage

### UI formatting tests

Add or update formatting tests to verify:

- secondary cache summary is omitted when empty
- read-only and read+write cache summaries render correctly
- reasoning summary renders only when present
- shared tooltip/help copy remains aligned with the intended semantics

### UI behavior tests

Add targeted tests in `src/ui/analytics_view.rs` for:

- section copy with partial coverage
- row rendering with and without cache/reasoning data
- unavailable rows still showing `—`

## Final Recommendation

Proceed with a conservative extension of the current token UX:

- keep the existing `SessionDetail` structure
- extend Analytics aggregates to include cache and reasoning counters
- expose cache visually but separately from totals
- centralize wording in shared formatting helpers

This delivers better observability and better semantics without widening the UI
surface or weakening the product's current caution around cross-provider token
meaning.
