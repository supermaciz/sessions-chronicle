  La niche de Sessions Chronicle

  C'est la seule application native GNOME/GTK4 + Libadwaita pour Linux.

  Ce n'est pas un détail cosmétique. Ça implique concrètement :

  - Intégration bureau réelle : thème système (dark mode automatique, couleurs
  d'accent), accessibilité GTK, raccourcis GNOME standards
  - Flatpak natif : sandboxing, distribution via GNOME Software / Flathub, mises
   à jour intégrées
  - Pas de serveur local à gérer : contrairement à AgentsView ou Claude Code
  Viewer, aucun daemon en arrière-plan
  - Pas d'Electron/webview : contrairement à Tauri, c'est du vrai GTK —
  empreinte mémoire et démarrage d'un niveau différent

  Ce que Sessions Chronicle fait déjà bien vs. la concurrence

  - Inspection des subagents en pane dédié — rare dans la concurrence
  - Token usage détaillé (cache read/write, reasoning) par session
  - 4 assistants avec parseurs dédiés et traitement en streaming (pas de
  chargement fichier entier)

  La vraie question

  Est-ce qu'un utilisateur Linux qui tient à un bureau GNOME cohérent va choisir
   AgentsView (ouvrir un navigateur) ou Claude Code History Viewer (app Tauri,
  look générique) plutôt qu'une app native Libadwaita ?

  Pour ce profil d'utilisateur, Sessions Chronicle n'a pas de concurrent direct.
   Le marché est petit mais non contesté.

  Sans intérêt ? Non. Niche ? Oui — et assumée.

❯ En dehors de l'UI, quel peut etre l'interet de Sessions Chronicle ?           

● Bonne question — elle force à aller au-delà du positionnement "app GNOME bien
  faite".

  L'insight fondamental

  Les sessions d'AI assistant sont un actif de connaissance personnelle qui dort
   dans des fichiers JSONL bruts, non structurés, non interrogeables. Sessions
  Chronicle les transforme en base de données relationnelle + FTS5.

  C'est le même saut qu'entre "des notes en .txt éparpillées" et une vraie base
  de notes.

  ---
  Ce que ça rend possible concrètement

  Mémoire de travail longue durée
  Tu as résolu un bug obscur avec Claude il y a 4 mois. Tu te souviens vaguement
   du sujet. Une recherche FTS5 sur les messages — pas seulement les titres —
  retrouve la session en secondes, avec highlighting dans le transcript.

  Analyse de ta propre pratique
  - Quels projets consomment le plus de tokens ?
  - Est-ce que tu utilises vraiment plusieurs assistants ou juste Claude ?
  - Tes sessions durent-elles plus longtemps sur certains types de tâches ?

  L'analytics actuelle (heatmap, assistant breakdown) n'est qu'un début.

  Audit post-mortem de runs complexes
  Avec l'inspection des subagents, tu peux retracer exactement ce qu'un agent
  multi-niveau a fait — quelle branche a été lancée, dans quel ordre, avec quels
   tool calls. C'est utile pour débugger une stratégie d'agentification, pas
  seulement pour lire une conversation.

  La base de données est interrogeable directement
  SQLite standard. Rien n'empêche de faire SELECT * FROM sessions WHERE 
  project_path LIKE '%mon-projet%' ou d'exporter vers un autre outil. C'est un
  format durable, pas un lock-in applicatif.

  ---
  Ce que ça pourrait devenir (directions naturelles)

  - Export : markdown, JSON structuré, pour alimenter un wiki ou une base
  Obsidian
  - Patterns de prompt : détecter les formulations qui mènent aux meilleures
  réponses dans ton historique
  - Corrélation avec git : relier une session à un commit ou une PR (le
  project_path est déjà stocké)
  - MCP server : exposer ta mémoire de sessions à un AI assistant via le
  protocole MCP — "cherche dans mes anciennes conversations ce qu'on avait
  décidé sur l'auth"

  ---
  En résumé

  L'UI est la partie visible. La valeur sous-jacente c'est : tu as des centaines
   d'heures de travail avec des AI assistants — Sessions Chronicle est la seule 
  infrastructure qui rend cet historique utile après coup.

  Les concurrents ont souvent la même surface fonctionnelle mais aucun ne pose
  clairement la question "comment est-ce que cet historique devient un actif
  réutilisable ?"
